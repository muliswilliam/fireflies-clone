# Submission notes

Firefly Notes is a simplified Fireflies.ai: record a Meeting, read its Transcript, get a Summary with Action Items. It runs at [fireflies.williammuli.dev](https://fireflies.williammuli.dev); the code is at [github.com/muliswilliam/fireflies-clone](https://github.com/muliswilliam/fireflies-clone). This document is the brief's "what you did" write-up. The [README](../README.md) has setup, run, test and deploy instructions.

## What was built

- **Meetings list**: newest first, with title, date, duration, Speaker count and Status, a title search, Sample badges, and a New meeting call to action.
- **New meeting**: a prefilled form (title, 2 to 6 uniquely named Speakers, optional agenda) with inline validation. Two ways in: **Start recording** runs a live timer with a pulsing indicator and a Stop button; **Instant Meeting** picks a duration (5, 15, 30 or 60 minutes) and skips straight to processing.
- **Processing**: stopping a Recording kicks off Transcribing then Summarizing on the server; the page polls and re-renders as the Status stepper advances. A failure shows the failing step and the reason with a Retry that resumes at that step and reuses work already done.
- **Transcript**: speaker-attributed, timestamped Utterances, one colour per Speaker, sized to the Recording (one Utterance per 12 seconds, clamped to 8 to 80). Click a timestamp to highlight a moment.
- **Summary**: an Overview, 3 to 7 Key Takeaways and up to 10 Action Items, each owned by a Speaker or nobody with an optional due date. Action Items can be ticked done; the Summary can be regenerated, copied as Markdown or downloaded as a `.md` file.
- **Manage**: rename inline, delete after confirming (Speakers, Transcript, Summary and Action Items go with it).
- **Sample Meetings**: three checked-in fixtures seeded idempotently on every start so the workspace is never empty.
- **Operations**: everything configured by environment variables, a health route, a global daily Meeting cap, a multi-stage Docker image that migrates and seeds on start, GitHub Actions running lint, typecheck, unit and integration tests, Playwright e2e and a Docker boot check, and auto-deploy to a self-hosted Dokploy on every push to `main`.
- **Look and feel**: neutral shadcn palette with one indigo accent, system light and dark, loading skeletons, empty and error states, a laptop layout that degrades to one column on a phone.

## Approach

I spent the first block on thinking rather than code: an interview-style grilling of the brief, then a glossary ([`CONTEXT.md`](../CONTEXT.md)) that fixes the vocabulary (Meeting, Recording, Transcript, Utterance, Speaker, Summary, Action Item, Meeting Status, Sample Meeting, Instant Meeting), five architecture decision records, a spec, and a ticket breakdown into eleven tickets, ten vertical slices plus this polish pass. Every ticket after that was a thin end-to-end slice, test-first where a seam made that cheap, merged through a pull request with CI green.

The code is layered so behaviour lives in one place: UI (server components with small client islands) calls thin server actions and route handlers, which call a single **Meeting service** that owns every rule and Status transition, over a Drizzle repository on Postgres. The service depends on two small interfaces, `TranscriptionProvider` and `SummarizationProvider`, with a deterministic fake for tests and a Claude implementation for production. The Claude adapter streams one structured-output call per step, constrained by a JSON schema derived from the same Zod shapes that guard the database, and re-validates every answer.

Testing follows the layers: Vitest unit tests for the pure rules and prompt builders, Vitest integration tests for the service against a real Postgres, Playwright e2e for every user story including failure and Retry (via test-only fault injection switched on by an environment flag), and a live Claude smoke test that only runs when explicitly enabled.

## Key decisions

Each has a record in [`docs/adr/`](adr/) with the alternatives considered.

- [ADR-0001](adr/0001-simulated-recording-generated-transcript.md): the Recording is simulated and the Transcript is generated by an LLM. No audio, no speech-to-text; a real vendor is one more provider implementation.
- [ADR-0002](adr/0002-fire-and-forget-pipeline-with-status-column.md): the pipeline is fire-and-forget with a status column, not a job queue. Cheap, restart-unsafe, with pg-boss as the named upgrade path.
- [ADR-0003](adr/0003-single-shared-workspace-no-auth.md): one shared workspace, no authentication.
- [ADR-0004](adr/0004-transcript-and-summary-as-jsonb.md): Transcript and Summary are JSONB documents; Speakers and Action Items are rows.
- [ADR-0005](adr/0005-global-daily-meeting-cap.md): a global daily cap on Meeting creation is the only abuse guard.

Smaller calls worth naming: Next.js App Router with server actions to keep the request layer thin; Drizzle with checked-in SQL migrations run on container start; shadcn/ui on Base UI for accessible primitives without a design system to fight; Dokploy on a server I already run rather than a PaaS, so deploy is `git push`.

## Assumptions

- The reviewer wants a working link first and a readable repository second, so scope went to the end-to-end path and its polish, not to accounts, sharing or billing.
- Nothing is recorded or transcribed from speech; the Transcript is plausible fiction steered by the title, Speakers and agenda.
- One public workspace with a daily cap is acceptable for a demo; the cap protects the API bill, not the data.
- A Meeting caught mid-pipeline by a server restart stays in flight; this is documented rather than solved.
- Dates render in the server's time zone in a fixed `en-GB` format.
- Claude Opus 5 is the production model; the fake provider is used by every automated test so CI is free and deterministic.

## AI tools used

- **Claude Code** wrote nearly all of the code, tests and documentation, working ticket by ticket from the spec, with me grilling the plan, reviewing diffs, and steering design and scope. The time log below is the active time from those sessions.
- **Claude Opus 5** (through the Anthropic SDK) is the runtime model that writes Transcripts and Summaries in the deployed app. It also wrote the three Sample Meeting fixtures once, which were then hand-checked and committed.
